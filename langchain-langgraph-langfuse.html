LangChain, LangGraph and Langfuse, explained with one agent

Engineers often mention these three tools in the same breath. They do three different jobs. We'll use one example throughout: a research assistant that takes a question, searches the web, reads the results and writes a short report.

1 · The big picture

Three tools, three jobs

Think of building an as running a restaurant kitchen. You need ingredients and utensils, a recipe that says what to do and when, and a camera that records how each dish was actually made.

2 · LangChain · build

LangChain: a box of building blocks for LLM apps

LangChain is an framework, available for Python and JavaScript. It gives developers standard parts for common LLM tasks, so they don't have to build each one from scratch.

The main parts, in our research assistant

Models

One standard way to call many LLM providers. Switching providers can be a one-line change instead of a rewrite.

Ours: a large model writes the report, a small, cheap one grades search results.

Prompts

A is a reusable prompt with blanks to fill in, such as {question} and {notes}.

Ours: "Write a 150-word report answering {question} using only these notes: {notes}"

Tools

Wrappers that let the model ask for actions, like searching. LangChain has ready-made for hundreds of services.

Ours: web_search and fetch_page.

Memory

Ways to keep the conversation and earlier results so later steps can use them. In recent versions, this is mostly handled by LangGraph's saved state.

Ours: the question, search results and notes carried from step to step.

Chains

A links parts in a fixed line: prompt, then model, then clean up the output.

Ours: the "write the report" step is a small chain.

Also included

Document loaders, text splitters, and for searching your own documents, plus parsers that turn model output into structured data.

What it looks like in code

# Simplified. The "|" symbol means "then".
model  = init_chat_model("provider:large-model")   # change this line to switch provider
prompt = ChatPromptTemplate.from_template(
  "Write a 150-word report answering {question} using only these notes: {notes}")
write_report = prompt | model | StrOutputParser()
report = write_report.invoke({"question": q, "notes": notes})

Four lines replace a lot of hand-written code for building the request, calling the provider's and reading the reply.

Makes easier

  • Swapping between model providers
  • Connecting common tools, databases and document stores with ready-made integrations
  • Getting a prototype working in days
  • Hiring: many engineers already know it

Can feel heavy

  • Many layers of . When something breaks, the error can be hard to trace back.
  • Overkill for one or two model calls, where the provider's own SDK is simpler
  • Fast-moving: past versions changed often, so upgrades can take work
  • Adds your team must keep up to date

3 · LangGraph · orchestrate

LangGraph: an agent drawn as a map of steps

LangGraph is an open-source library from the same company as LangChain. You describe your agent as a : boxes for steps and arrows for what can come next. It can be used with or without LangChain.

Why a straight-line chain isn't enough

Is a graph still an agent? In module 1's terms, a developer draws this map, and the model decides which arrow to take and what to search. That's level 4 on module 1's spectrum: an agent with fences. A fully open agent loop is also a graph, just a tiny one (model → tools → model), and LangChain's create_agent builds exactly that.

The key ideas

Nodes

A is one step, such as search or write. Inside, it can use LangChain parts or any other code.

Edges and branches

An is an arrow to the next step. A picks the route based on results: good results go to read, poor ones to rewrite_query.

State

The is a shared notebook passed between steps: the question, results, notes and draft. Every node reads it and updates it.

Loops and retries

Arrows can point backwards to try again. A re-runs a step automatically when it errors, for example a search that times out.

Checkpoints

A saves the state after every step. If the server crashes, the run picks up where it stopped instead of starting over.

Human approval

An pauses the run so a person can approve, edit or reject. It can wait minutes or days, then resume.

The research assistant as a graph, in code

# Simplified. This is the same graph you clicked through in the demo.
graph = StateGraph(ResearchState)              # state: question, query, results, notes, draft…
graph.add_node("plan", plan)
graph.add_node("search", search, retry_policy=RetryPolicy(max_attempts=3))
graph.add_node("grade", grade)
graph.add_node("rewrite_query", rewrite_query)
graph.add_node("human_review", human_review)  # calls interrupt() to wait for a person
# …read, write, no_sources

graph.add_edge(START, "plan")
graph.add_edge("plan", "search")
graph.add_edge("search", "grade")
graph.add_conditional_edges("grade", route_after_grade)  # good → read · poor → rewrite_query · 2 tries → no_sources
graph.add_edge("rewrite_query", "search")          # the loop

app = graph.compile(checkpointer=saver)       # checkpoints let a paused run resume later

4 · Langfuse · observe

Langfuse: a flight recorder for your LLM app

Langfuse is an open-source platform for of LLM apps. It has three main jobs: tracing, prompt management and evaluation. Your team can use Langfuse's cloud version or it.

A separate project. Langfuse is made by a different company from LangChain and LangGraph. It works with them through a ready-made connector, and it works just as well without them: with plain provider SDKs, other frameworks, or anything that speaks . LangChain's own product for this job is called LangSmith.

What a trace looks like

A is the full record of one run. Inside it are nested pieces called observations.

TRACE research-assistant 8.4 s · $0.0158
SPAN plan 1.6 s
GENERATION chat-large 780 tok · $0.0044
SPAN search 0.9 s
TOOL web_search 0.9 s
SPAN write 3.0 s
GENERATION chat-large 2,200 tok · $0.0102
SCORE citations_valid = 1.0
TRACE One run
Everything that happened for one question, with total time and cost.
SPAN One step
A is a timed piece of work, such as one node of the graph.
GENERATION One LLM call
A shows the exact prompt, the reply, the model, the and the cost.
SCORE A quality grade
Added by code checks, an or user feedback such as a thumbs-down.

How it helps you debug

Cost

"Why did costs double this week?"

Filter traces by cost and see which step and which model spends the most. For example, a loop that searched 5 times instead of once.

Latency

"Why is it slow?"

The timeline bars show where time goes. is often one slow tool, or steps that could run at the same time but don't.

Wrong answers

"Why did it say that?"

Open the trace for a bad report. Check what the search returned, what the model was given, and the exact step where it went wrong.

Prompt management and evaluation

Prompt management

Prompts are stored and versioned in Langfuse rather than in the code. A PM or engineer can change the report prompt, label it "production" and roll it back if it's worse, without a code release. Each trace shows which prompt version produced it.

Evaluation

Score traces automatically (citation check, LLM-as-judge), collect user feedback, and run a saved set of test questions, called a dataset, against a new prompt or model before it ships. An turns "it seems better" into a number.

# Simplified. With LangChain/LangGraph: pass one handler.
handler = CallbackHandler()
app.invoke({"question": q}, config={"callbacks": [handler]})

# Without them: mark your own functions to be traced.
@observe()
def research(question): ...

A handler is a listener that LangChain notifies at every step, so Langfuse can record it.

5 · How they work together

The same research assistant, before and after

"Before" is a plain script written by a good engineer. "After" splits the work between the three tools. Everything on the right can be built by hand. The real question is whether you want to build and maintain it yourself.

SituationBefore: a plain script, done wellAfter: all three tools
Switch to another model providerWrite and keep up your own small wrapper around each provider's SDKChange one line LangChain
Search returns junkAdd a grading call, an if-statement and a loop counterGrade step and a conditional edge, drawn on the map LangGraph
Search tool times outWrite a retry with back-off around the callA retry policy on the step LangGraph
Report needs sign-offSave progress to a database and write your own resume logicInterrupt and checkpoint, resume any time LangGraph
"Why was Tuesday's report wrong?"Log every prompt, reply and tool call yourself, then build a way to search the logsOpen that trace and see every step Langfuse
"What does one report cost?"Record token counts and keep a price table up to dateCost per run, per step, per model Langfuse
Improve the report promptCode change and release, or build your own prompt storeNew prompt version, compare with an eval, roll back in a click Langfuse
LangChain does

The model calls in plan, grade and write, the prompt templates, and the web_search and fetch_page tools.

LangGraph does

The order of steps, the poor-results loop, the retry on timeout, the human approval pause and the saved state.

Langfuse does

Records every run as a trace, adds scores, stores the prompts and powers the cost and quality dashboards.

You don't have to use all three. Many teams use LangGraph without LangChain's extras, or call providers directly and add only Langfuse. Each piece can be swapped for an alternative.
PM takeaway

The "after" version isn't smarter. It saves you building and maintaining the plumbing that production needs. If you only need one or two rows of this table, plain code may still be the better choice.

6 · Decision guide

Which ones does your team need?

ToolUse it when…Skip it when…
LangChainYou want to try several model providers, need ready-made integrations (search, databases, documents), or want a fast prototype.It's one or two model calls, the team prefers the provider's own SDK, or you want the fewest dependencies possible.
LangGraphYour agent loops, branches, retries, waits for human approval, runs for a long time, or involves several agents.The flow is a straight line, or a simpler agent toolkit already covers what you need.
LangfuseAnything LLM-based going to real users: you need cost per feature, debugging, prompt versions or evals. Self-hosting helps when data must stay in your own systems.It's a throwaway prototype, or the company already uses another LLM tracing tool, such as LangSmith.

Questions to ask your engineering team before choosing a stack

Do we need it?

  • What's the simplest version that would work? Do we need a framework at all?
  • Which parts of our flow need loops, retries or human approval?
  • How hard would it be to swap one of these tools out later?

Will it hold up in production?

  • If a run crashes halfway, can it resume? Where is the state saved?
  • What limits stop a loop from running forever, and what does a run cost at most?
  • Which versions are we on, and who owns upgrades?

Can we see what it does?

  • Where do traces go, and who can see them?
  • Do traces contain personal or client data? Should we hide it or self-host?
  • How will we spot cost spikes and quality drops? Who gets alerted?

Can we improve it safely?

  • How do we change a prompt: code release or prompt management? Who can do it?
  • What's our eval set, and does it run on every change?
  • How do user complaints turn into new test cases?

Who makes what

  • LangChain and LangGraph: open source, both from LangChain Inc. They work together, and LangGraph also works on its own.
  • Langfuse: open source, from a separate company. Cloud or self-hosted. Works with any framework.
  • LangSmith: LangChain's own tracing and evaluation product, an alternative to Langfuse.
  • Alternatives: provider SDKs and agent SDKs, LlamaIndex, CrewAI, Temporal, Phoenix and more. See the decision guide.

Words you'll hear

  • Chain: fixed sequence of steps
  • Node / edge: a step / an arrow between steps
  • State: the shared notebook between steps
  • Checkpoint: saved state, so runs can resume
  • Interrupt: pause for a person
  • Trace / span / generation: a run / a step / an LLM call
  • Score / eval: a quality grade / a test across many examples

PM takeaways

  1. Build, orchestrate, observe: three different jobs.
  2. LangChain speeds up building, but can be heavy for simple apps.
  3. Loops, branches, retries or approvals mean you need a graph.
  4. Tracing is how you find out about quality, cost and speed.
  5. The "after" version is sturdier, not smarter.
  6. Choose the smallest stack, and trace from the first day.

Numbers to ask for

  • Cost per run, and the most one run can cost
  • p95 latency, and the slowest step
  • Retries and loops per run
  • Eval pass rate, and how it changed after the last release
  • Human approval rate and rejection rate

3 common mistakes teams make with these tools

1

Adopting the whole stack on day one

What it looks like
A feature that is really one prompt and one API call gets wrapped in chains, graphs and agents. It becomes harder to debug and slower to change than plain code.
Fix
Start with the simplest version. Add LangChain or LangGraph when a real need appears, such as a second provider, a loop or an approval step.
2

Graphs without limits or checkpoints

What it looks like
A "try again" loop has no maximum, so a bad day for the search tool burns through budget. Runs waiting for approval are lost when the server restarts.
Fix
Cap every loop and retry (our graph gives up after 2 rewrites). Turn on a checkpointer, and test the failure paths, not just the happy path.
3

Treating tracing as a checkbox

What it looks like
Langfuse is switched on, but no one reviews traces, sets cost alerts or adds scores. Meanwhile, traces quietly store customers' personal data.
Fix
Agree on who reviews traces each week. Set alerts on cost and errors, score quality automatically, and hide sensitive fields before they're sent.
