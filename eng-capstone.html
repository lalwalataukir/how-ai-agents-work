1 · The project

    
Finish the research assistant, or build your own

    
The research assistant already has every part, so finishing it well is a fine capstone. Your own idea shows more, if it passes these tests.

  

  

    
A good capstone idea
    
      
  • You are a real user, with a real need
    • 
      
  • You have the data, and it's fine to use
    • 
      
  • It needs retrieval or tools, not only a prompt
    • 
      
  • One flow can work end to end in two weekends
    • 
      
  • It's safe to put online with limits
    • 
    

    
Ideas that fit
    
      
  • A study helper over your course PDFs
    • 
      
  • A meeting-notes assistant that finds decisions and owners
    • 
      
  • Q&A over a product's public docs and changelog
    • 
      
  • A reading-list agent that summarises and files papers
    • 
    

  

  
Avoid ideas built on other people's personal data, such as CVs or emails. You'd need consent and stronger safeguards than a portfolio project should take on.

3 · Scope it to ship

    
One flow, working, deployed, before anything else

    
Most side projects never ship because they keep growing. An  is the smallest thing that does the main job end to end, for real.

  

  

    
Must
The one main flow, deployed, with evals and limits. If any of these is missing, it isn't done.

    
Should
One or two improvements, only after "must" is live. For example, a friendlier page or keyword search.

    
Won't, for now
Logins, multiple users, a mobile app, five more tools. Writing them down makes saying no easy.

  

  
Timebox it. Two weekends for the "must" list. If it isn't live by then, cut scope, not quality: drop a feature, never the evals or the limits.

4 · A README that sells it

    
One minute to make the case

    
A reviewer opens your repo and gives it a minute. The  has to show what it does, prove it works, and invite them to look closer.

  

  
    
    
  1. First screen: what it does in one sentence, the live link, the video.
    2. 
    
  2. How it works: four bullets, one per part, naming the real tools.
    3. 
    
  3. Evidence: the eval score and how it's gated, the security defences and their tests, the cost per 1,000 questions.
    4. 
    
  4. Run it yourself: commands that work on a clean machine.
    5. 
    
  5. What's next: two honest improvements. It shows you know the limits.
    6. 
  

  
Numbers beat adjectives. "95% on 20 eval cases, checked on every pull request, about $0.35 per 1,000 questions" says more than "robust and cost-effective".

7 · Show it

    
Make it easy to find, and ready to talk about

    
A  project only helps if people see it, and you can explain it.

  

  

    
Make it findable
Tag a , v1.0. Pin the repo on your GitHub profile. Link it from your CV and LinkedIn.

    
One line for your CV
"Built and deployed a research agent (Python, Claude API, Chroma, FastAPI) with 20 eval cases gating every merge; chose the model with evals at 1/20 the cost of the next option."

    
Ready for questions
Be ready to explain your trade-offs: chunk size, what memory keeps, the model choice, which limits and why, and a failure you found in a trace and fixed.

  

  
That last box is where the PM modules pay off. Engineers who can explain why a system is built the way it is, in terms of users, cost and risk, are the ones teams trust with agents.

If it breaks
SPEC.md still has 13 <placeholders> to fill in
Search the file for < and replace each placeholder with your own words, angle brackets included.
API keys in: .env
.env isn't in .gitignore, so it would be published. Add it. If it was ever committed, run git rm --cached .env and revoke the key in the Console.
README has no "**Try it:** https://..." line
The check looks for that exact shape: **Try it:** https://your-app.onrender.com on one line.
the live app answered ReadTimeout
The server didn't answer within 90 seconds. Open the URL in a browser, and check Render's logs for a crash.

Learn from others

    
3 common portfolio mistakes

  

  

    
1
A project that never ships

      
What it looks like
Months of adding features to something only you have seen.

      
Fix
Write the "won't" list, deploy the "must" list, then improve what's live.

    
2
A README with no evidence

      
What it looks like
"An AI-powered assistant using cutting-edge LLMs", and no link, score or video.

      
Fix
Live link and video first, then the eval score, the cost and how it's tested.

    
3
A demo that runs up a bill, or leaks a key

      
What it looks like
A public app with no limits, or a key in the repo's history.

      
Fix
Limits in code, a spend limit in the Console, and check_portfolio.py before every share.
