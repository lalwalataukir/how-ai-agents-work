Choosing models: pick with evidence, not hype

There's always a newer, bigger model. The right one for your product is the cheapest and fastest one that passes your evals. This module compares models on , shows the levers before switching models, covers running on your own computer, and sorts out when fine-tuning, prompting or RAG is the answer. You'll run your eval set on three Claude models and a local one, and write down your choice.

1 · Three numbers

Quality, cost and speed, for your task

Every model choice trades the same three things. Measure all three on your own task before deciding: a model's reputation tells you little about your questions.

Quality

Your eval score from E8, graded the same way for every model. Not a public leaderboard, which measures someone else's task.

Cost

Per 1,000 questions, from real token counts: agent loops multiply the per-token price by every call and page.

Speed

Time to first words and to the full answer (E9). Bigger models think and write more slowly.

ModelInput, per million tokensOutput, per million tokensFor

2 · Your evals decide

Run the same evals on every candidate

The eval set you built in E8 is your benchmark. Run it on each model with everything else fixed: same agent code, same tools, same judge.

Keep the judge fixed

If the judge changed with the model, you'd be comparing judges. The lab uses one judge for all.

Mind the noise

On 20 cases, one case is 5 points. A 95% against 100% gap is one answer: read it before you pay 20 times more.

Test the hard cases

Easy questions make every model look equal. Add the multi-step questions your users really ask, and the gaps appear.

3 · Effort and routing

Levers to try before switching models

Changing model is the biggest lever, and the one that most often costs quality. Try the cheaper ones first, and measure each with your evals.

LeverWhat it doesWatch out for
Better prompts and toolsFixes the failures your traces show, on every modelNeeds the eval set to prove it worked
Prompt caching (E9)Cuts the cost of everything repeated, without changing answersAnything changing at the start of the prompt breaks it
Less thinking means fewer tokens and faster repliesHard questions may need more. A stronger model at lower effort can cost less than you'd expect and still pass
A cheap model for easy questions, a strong one for hard onesYou need a reliable way to tell them apart, and each model keeps its own cache

4 · Open and local models

Models that run on your own computer

such as Qwen, Gemma, Llama and gpt-oss can be downloaded and run yourself. makes that a two-command job, and since version 0.14 it understands the Claude Messages API, so the SDK you know works with a different address.

What you gain

Data never leaves the machine. No bill per token. Works offline. You choose exactly which version runs, and it never changes under you.

What it costs

Hardware: an 8-billion-parameter model wants 8 GB of free memory, and bigger ones need a strong GPU. Slower answers on a laptop. Weaker at multi-step tool use. In production, you run, scale and secure the servers.

Local models are to fit in memory, which costs a little quality. They're a good fit for private data and simple steps, such as answering from retrieved notes. For agents that plan and use tools, check them against your evals before trusting them.

5 · Fine-tune, prompt or RAG?

Match the fix to the problem

"Should we fine-tune?" usually means "the model doesn't do what we want". The answer depends on what exactly is missing.

The problemReach forWhy
It doesn't know our factsRAG (E6)Retrieval brings current facts, with citations, and updates the moment your documents do
It ignores our format or rulesPrompting, examples and structured outputs (E4)Fast to change and test; structured outputs guarantee the shape
It can't do a stepA tool (E5) or a stronger modelGive it the ability, or the reasoning, it's missing
A narrow task at huge volume needs a particular style, maybeOnly with thousands of good examples, an eval set, and someone to retrain it as models change

Fine-tuning is the last resort, not the first. It teaches style and narrow behaviour better than facts, can't cite sources, and locks you to one model version. Current Claude models aren't fine-tuned through the Claude API; open-weight models can be, with tools such as Hugging Face's.

6 · Write it down

A decision record for the model

A model choice is a product decision with numbers behind it. A short keeps them: the options, the evidence, the choice, what you gave up, and when to look again.

For your team

Six months on, nobody remembers why it's Haiku. The record does, with the eval results that justified it.

For reviewers

In a portfolio, "I chose X because of these numbers" shows judgement, not just code. E12 uses it.

For later

"Revisit when" names the triggers: a score drop, a new model, a price change, harder questions.

Lab · on your laptop

Compare models on your evals, and choose one

Two new files: one runs your eval set on three Claude models, the other tries a model on your own computer. Then you write down the choice.

  1. 1

    Write compare_models.py

    It runs the eval set from E8 against your E10 agent once per model, keeps the judge the same, and prints quality, cost and speed side by side.

    compare_models.py
    """E11 lab: run the eval set on several models, and compare quality, cost and speed. Run it with:    uv run compare_models.py      # every case on every model    uv run compare_models.py 5    # the first 5 cases: a quick, cheap look"""import jsonimport statisticsimport sysimport timefrom pathlib import Path import anthropic import agentimport run_evals # Dollars per million tokens: input, output, and input read from the cache.# Writing to the cache costs 1.25 times the input price.MODELS = {    "claude-haiku-5-5": (0.10, 0.50, 0.01),    "claude-sonnet-5-5": (2.00, 10.00, 0.20),    "claude-opus-5-5": (4.00, 20.00, 0.20),}REPORT = Path(__file__).parent / "model_report.json"  def cost_of(model, run):    """What one run cost at this model's prices, from the token counts the agent reports."""    price_in, price_out, price_read = MODELS[model]    dollars = (run["tokens_in"] + 1.25 * run["cache_written"]) * price_in + run["cache_read"] * price_read    return (dollars + run["tokens_out"] * price_out) / 1_000_000  def evaluate(model, cases):    """Run every case on one model. The judge stays the same, so only the model changes."""    agent.MODEL = model    agent.PRICE_IN, agent.PRICE_OUT = MODELS[model][:2]  # so the agent's own cost limit uses the right prices    passed, costs, seconds = 0, [], []    for case in cases:        start = time.perf_counter()        try:            for event in agent.steps(case["question"], [], approve=lambda name, args: False):                pass  # the last event is "done"            problems = run_evals.code_checks(case, event["answer"])            if not problems:                verdict, _ = run_evals.judge(case, event["answer"])                problems = [] if verdict.passed else ["judge: " + verdict.reason]            costs.append(cost_of(model, event))        except anthropic.APIError as error:            problems = [f"API error: {error}"]        seconds.append(time.perf_counter() - start)        passed += not problems        print(f"  {model:<18} {case['id']:<16} {'pass' if not problems else 'FAIL'}  {seconds[-1]:5.1f} s")    return {"model": model, "score": passed / len(cases),            "per_1000": round(1000 * statistics.mean(costs), 3) if costs else None,            "median_seconds": round(statistics.median(seconds), 1)}  def main(limit=None):    cases = json.loads(run_evals.CASES.read_text(encoding="utf-8"))[:limit]    rows = [evaluate(model, cases) for model in MODELS]    print(f"\n{'model':<18} {'score':>6} {'per 1,000 questions':>20} {'median time':>12}")    for row in rows:        cost = f"${row['per_1000']:.3f}" if row["per_1000"] is not None else "-"        print(f"{row['model']:<18} {row['score']:>6.0%} {cost:>20} {row['median_seconds']:>10.1f} s")    good_enough = [row for row in rows if row["score"] >= run_evals.MIN_SCORE and row["per_1000"] is not None]    best = min(good_enough, key=lambda row: row["per_1000"]) if good_enough else None    print(f"\nCheapest model at or above {run_evals.MIN_SCORE:.0%}: {best['model'] if best else 'none'}")    REPORT.write_text(json.dumps({"cases": len(cases), "min_score": run_evals.MIN_SCORE, "models": rows}, indent=2), encoding="utf-8")    return best  if __name__ == "__main__":    main(int(sys.argv[1]) if len(sys.argv) > 1 else None)
    • MODELS holds each model's real prices, including cache reads, so costs are worked out at the right rate.
    • evaluate points the agent at one model by changing agent.MODEL, which every call reads, and its prices, so the agent's own cost limit stays right.
    • The checks and the judge come from run_evals.py, unchanged. Only the model being tested changes, so the comparison is fair.
    • main prints the table, names the cheapest model at or above MIN_SCORE, and saves model_report.json.

  3. 3

    Read the differences

    Open Langfuse and filter by the eval tag. For each case that passed on one model and failed on another, open both traces:

    • Did the weaker model plan worse, read the wrong page, or misread the right one?
    • Would a better tool description or prompt fix it on the cheap model?
    • Is the failure a kind your users would notice?
  4. 4

    Try a model on your own computer

    Install Ollama from ollama.com/download, then download a model of about 5 GB. It needs 8 GB of free memory to run well:

    Terminal
    ollama pull qwen3:8b

    Ollama understands the same Messages API as Claude, so the same SDK can talk to it: only the address changes. Create local_rag.py next to rag.py:

    local_rag.py
    """E11 lab: answer from your notes with a model running on your own computer, through Ollama,and compare it with Claude on the same question. First install Ollama from ollama.com and download a model:    ollama pull qwen3:8bThen run:    uv run local_rag.py "How much will I pay if I bring a book back late?""""import sysimport time import anthropic import rag  # E6: search your notes, and answer with Claude LOCAL_MODEL = "qwen3:8b"  # any model you've pulled with Ollama# Ollama understands the same Messages API, so the same SDK works: only the address changes.local = anthropic.Anthropic(base_url="http://localhost:11434", api_key="ollama")  # Ollama ignores the key  def answer_locally(question, hits):    """The same prompt as rag.answer, sent to the local model. No data leaves your computer."""    sources = "\n".join(        f'<source file="{hit["source"]}" page="{hit["page"]}">\n{hit["text"]}\n</source>' for hit in hits    )    response = local.messages.create(        model=LOCAL_MODEL, max_tokens=2000, system=rag.SYSTEM,        messages=[{"role": "user", "content": f"<sources>\n{sources}\n</sources>\n\nQuestion: {question}"}],    )    return "".join(block.text for block in response.content if block.type == "text")  def compare(question):    hits = rag.search(question)    if not hits:        print("Nothing close enough in your notes.")        return    for name, ask in (("Claude Haiku 5.5", lambda: rag.answer(question, hits)),                      (f"{LOCAL_MODEL}, on this computer", lambda: answer_locally(question, hits))):        start = time.perf_counter()        try:            text = ask()        except anthropic.APIConnectionError:            text = "Could not reach Ollama. Is it running? Start the Ollama app, or run `ollama serve`."        print(f"--- {name} ({time.perf_counter() - start:.1f} s)\n{text}\n")  if __name__ == "__main__":    compare(" ".join(sys.argv[1:]) or input("Question: "))
    Terminal
    uv run local_rag.py "How much will I pay if I bring a book back late?"

  5. 5

    Write down your choice

    Create MODEL_CHOICE.md with your own numbers. Here's an example to start from:

    MODEL_CHOICE.md
    # Model choice: research assistant **Decision:** Claude Haiku 5.5 (`claude-haiku-5-5`), at the default effort.**Date:** 2026-10-20 · **Decided by:** you ## Options compared Run with `compare_models.py` on the 20 cases in `eval_cases.json`, one judge for all. | Model | Eval score | Per 1,000 questions | Median time ||---|---|---|---|| Claude Haiku 5.5 | 95% | $0.354 | 4.8 s || Claude Sonnet 5.5 | 100% | $7.075 | 7.9 s || Claude Opus 5.5 | 100% | $13.380 | 11.2 s || qwen3:8b on my laptop (RAG answers only) | not run on the full set | $0 | 19 s | ## Why - Haiku clears our minimum score of 85% with room to spare, at about 1/20 of Sonnet's cost.- Its one failure (`mccarthy-job`) was a wrong detail that a stronger model fixed. It isn't a pattern in our questions.- Visitors see the first words in under 4 seconds, which matters more for the web app than the last 5%. ## What we gave up - About one answer in twenty is less accurate than the bigger models would give.- The local model keeps data on the laptop, but was slower and missed citations on several answers. ## Revisit when - The eval score drops below 90% for two runs in a row.- We add harder, multi-step questions to the eval set.- A new model or a price change comes out.

    If you choose a different model, change MODEL and the prices in agent.py, and run the evals again before you merge.

  6. 6

    Make it yours

    Pick at least one:

    • Add three hard, multi-step questions to the eval set and run the comparison again. Does the cheapest good-enough model change?

    • Try a second local model, such as a smaller one if qwen3:8b was slow, and add it to your decision record.

If it breaks

Could not reach Ollama. Is it running? Start the Ollama app, or run `ollama serve`.
Ollama isn't running, or is on another port. Open the Ollama app; on a server, run ollama serve in a second terminal.
anthropic.NotFoundError: Error code: 404 - … model 'qwen3:8b' not found
The model isn't downloaded yet. Run ollama pull qwen3:8b, or set LOCAL_MODEL to a model from ollama list.
anthropic.RateLimitError: Error code: 429
The larger models have lower rate limits on new accounts. Run fewer cases (uv run compare_models.py 5), or wait a minute and run again.
Cheapest model at or above 85%: none
No model met MIN_SCORE. Read the failures: often a prompt or tool fix helps every model more than switching does.

Keep this

One-page cheat sheet

Same evals, same judge, every model → compare score, cost per 1,000 and time → pick the cheapest that passes → write it down → revisit when things change.

Compare

  • Your eval set, not leaderboards
  • One judge for every model
  • Cost per 1,000 real requests
  • Read failures, not only scores

Before switching

  • Fix prompts and tools
  • Cache what repeats
  • Try lower effort on a stronger model
  • Route only if you can tell hard from easy

Which fix

  • Missing facts: RAG
  • Wrong format: prompts and structured outputs
  • Missing ability: tools or a stronger model
  • Fine-tuning: rarely, with lots of data

Glossary

Learn from others

3 common model-choice mistakes

1

The biggest model, by default

What it looks like
The top model everywhere, 40 times the cost of one that would pass the same evals.
Fix
Start with the cheapest model that passes your evals, and move up only where the evals show you need to.
2

Choosing from a leaderboard

What it looks like
A model picked for its benchmark rank that does worse on your questions than the one it replaced.
Fix
Run your own eval set on the candidates. Benchmarks are a shortlist, not a decision.
3

Fine-tuning to add knowledge

What it looks like
Weeks spent training a model on company documents, which still makes things up and can't cite them.
Fix
Use RAG for facts. Keep fine-tuning for style or narrow behaviour, once prompting can't get there.
