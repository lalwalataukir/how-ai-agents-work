1 · Tracing

A trace is the agent's flight recorder

An agent run is a dozen steps you can't see from the final answer. A trace records each one as a : the plan call, every model call with its tokens and time, every tool call with its arguments and result, all nested under the run.

Claude calls, for free

The Anthropic SDK writes a span for every request in the standard. get_client() makes Langfuse their destination, so every Claude call is traced with no more code.

Your steps, with a decorator

@observe on steps makes each run one trace; on run_tool it records every tool call inside it.

Content is a choice

By default the SDK sends token counts, not prompts. ANTHROPIC_OPEN_TELEMETRY_TRACES_CONTENT_MODE=content adds prompts and replies: right on your laptop, a privacy decision in production (E10).

When an answer is wrong, the trace tells you why in a minute: the plan skipped your notes, a page failed to load, or the model ignored a result it had. Without it you'd be guessing.

2 · An eval set in code

Twenty questions with known good answers

An eval set is a file of test cases kept in git next to the code. Each case says what to ask and how to tell a good answer: words it must contain, and a reference for the judge.

One case from eval_cases.json
{  "id": "ai-term",  "question": "Who coined the term \"artificial intelligence\", and when?",  "expect": "answer",  "must_include": [    "McCarthy",    "1955|1956"  ],  "reference": "John McCarthy and colleagues, in their 1955 proposal for the 1956 Dartmouth workshop."}

Where cases come from

Questions real users asked, every failure you found in a trace, and edge cases you can think of. Start with 20; grow it every time something breaks.

Include "can't know"

Three of the lab's cases ask things nobody could know. A good agent says so; one that guesses fails.

Stable facts only

Pick questions whose right answer won't change next month, or the eval will fail while the agent is fine.

4 · Scores and thresholds

One number, and a line it mustn't cross

The score is the share of cases that pass every check. A , MIN_SCORE, turns it into pass or fail, through the program's .

Set it just below today

If the agent scores 95%, a threshold of 85% allows for run-to-run noise and still catches real drops.

Ratchet it up

When improvements hold for a week, raise the threshold so they can't quietly slip back.

Expect some noise

The same case can pass one run and fail the next. Look at which cases fail, not only the score, and rerun once before you panic.

5 · Evals in CI

A check on every pull request

runs checks on every proposed change. GitHub Actions reads a workflow file from your repo, starts a fresh machine, installs your project with uv, and runs the evals. If run_evals.py exits with 1, the check turns red.

Keys as secrets

The workflow needs your API key. It comes from an encrypted , never the code. GitHub hides it in logs.

Pull requests, not every push

Each run costs about $0.013 and four minutes. Running on pull requests checks what's about to be merged without paying for every small push.

Make it required

A branch rule can require the check to pass before merging, so nobody, including you, ships a drop by accident.

6 · The improvement loop

Traces find problems; evals keep them fixed

The two tools work as a loop, the same one module 10 describes for a team.

  1. Spot it: a bad answer, in testing or from a user.
  2. Trace it: open the run in Langfuse and find the step that went wrong.
  3. Capture it: add the question as an eval case. It should fail now.
  4. Fix it: change the prompt, a tool or a limit, until the new case passes.
  5. Gate it: open a pull request. The eval check confirms the fix and that nothing else broke.

Each eval run also lands in Langfuse, tagged eval, with its pass or fail attached to the trace as a score. When a case fails in CI, its trace is one filter away.

    run_evals.py
    """E8 lab: run the eval cases against the agent, score them, and fail when the score is too low. Run it with:    uv run run_evals.py      # every case    uv run run_evals.py 3    # the first 3 cases, for a quick, cheap check"""import jsonimport reimport sysfrom pathlib import Path import anthropicfrom langfuse import observe, propagate_attributesfrom pydantic import BaseModel import agent MIN_SCORE = 0.85  # below this the run fails: set it just under your current scoreJUDGE_MODEL = "claude-haiku-5-5"  # a stronger judge costs more and agrees with people more oftenCASES = Path(__file__).parent / "eval_cases.json"REPORT = Path(__file__).parent / "eval_report.json"JUDGE = """You grade a research assistant's answer to a question. <question>{question}</question><reference>{reference}</reference><answer>{answer}</answer> Pass the answer only if all of these are true:- It answers the question. When the reference says the answer can't be known, it says so instead of guessing.- Nothing in it contradicts the reference.- Every fact in it has a citation in square brackets.Give your reason in one sentence, then your verdict."""  class Verdict(BaseModel):    reason: str  # first, so the judge explains before it decides    passed: bool  def code_checks(case, answer):    """Checks that code can do exactly: free, instant, and the same every time."""    problems = []    for words in case["must_include"]:  # "1955|1956" means either one will do        if not any(word.lower() in answer.lower() for word in words.split("|")):            problems.append(f"doesn't mention {words}")    if case["expect"] == "answer" and not re.search(r"\[[^\]]+\]", answer):        problems.append("no citation")    if len(answer.split()) > 200:        problems.append("over 200 words")    if answer.startswith("Stopped"):        problems.append("hit a limit")    return problems  def judge(case, answer):    """An LLM judge for what code can't check: is it right, and does it say so when it doesn't know?"""    prompt = JUDGE.format(question=case["question"], reference=case["reference"], answer=answer)    response = agent.client.messages.parse(        model=JUDGE_MODEL, max_tokens=1000, output_config={"effort": "low"},        messages=[{"role": "user", "content": prompt}], output_format=Verdict,    )    usage = response.usage    return response.parsed_output, (usage.input_tokens * agent.PRICE_IN + usage.output_tokens * agent.PRICE_OUT) / 1_000_000  @observe(name="eval-case")def run_case(case):    """Run one case through the agent, then grade it: code checks first, the judge only if they pass."""    with propagate_attributes(tags=["eval"], metadata={"case": case["id"]}):  # Glossary

Learn from others

3 common eval mistakes

1

A judge for everything

What it looks like
Every check is an LLM call, so evals are slow, cost more, and disagree with themselves on obvious cases.
Fix
Use code for anything code can decide. Keep the judge for meaning, and skip it when the code checks already failed.
2

A threshold of 100%

What it looks like
One flaky case fails the build every other run, and people learn to ignore the red check.
Fix
Set the threshold a little under your usual score, fix or rewrite flaky cases, and raise it as the agent improves.
3

Evals that never grow

What it looks like
The same 20 cases for a year, while users hit problems none of them cover.
Fix
Every bug found in a trace becomes a case before it's fixed.
