What you'll build

The brief

The ticket you're picking up

Write it the way a team would: who it's for, what "done" means, and how you'll know. Every criterion below has a check in the starter's tests.

P1 · code-reviewerEstimate: 4 to 6 hours · Labels: python, claude-api, cli

As a developer, I want my changes reviewed before I commit them, so that bugs, security holes and leaked secrets are caught while they're cheap to fix.

Acceptance criteria

  • uv run reviewer.py reviews my uncommitted changes; --staged reviews only what I'm about to commit
  • Each finding has a file, a line that the change added, a severity (high, medium or low), the problem and a fix
  • Claude can read other files in the repo for context, but nothing outside it, and no .env files
  • The report is saved as review.md, worst findings first, with the cost of the review
  • It exits with code 1 on a high-severity finding, so a pre-commit hook can block the commit
  • It finds at least 4 of the 5 bugs planted in the sample change, for under $0.01 a review

What you practise

  • Parsing real developer data: a git diff (E2)
  • Structured output checked in code, with a retry (E4)
  • A tool-use loop, and a tool that's safe to give a model (E5)
  • Cost per run, and a command-line tool with exit codes (E3)

Why this project

Code review is one of the most common real uses of LLMs in engineering teams. Building one shows the whole pattern behind useful AI tools: give the model the right context, make it answer in a shape code can check, check it, and act on the result.

Architecture

How the parts fit

One file, reviewer.py, with a function for each box. The milestone that builds each part is in brackets, and dashed boxes can repeat.

  1. Get the diffgit_diff or a saved file (5)
  2. Number every lineparse_diff, format_change (1)
  3. Ask for a Reviewask, with output_format=Review (2)
  4. Read files if neededread_file inside the repo, at most 5 times (4)
  5. Check each findingcheck; ask again with the problems (3)
  6. Report and decidereview.md, exit code 0 or 1 (5)

The model only sees what the code gives it, and the code only acts on answers it has checked. That split is the design: Claude does the judgement, code does the counting, checking and deciding.

1 · Milestone 1 of 5

Read the diff

Turn the text of a diff into data: each changed file, and each line with its number in the new version. No API calls yet.

About 1 hourUses E2

Claude is good at spotting bugs and bad at counting lines. Paste a raw diff and ask "which line?" and the numbers drift. So the code does the counting: it numbers every line, and Claude only has to copy a number. Doing in code what code does well is a habit worth building.

What you write

  • parse_diff(text): returns a list of FileChange, one per file. Each has a path and rows: (mark, line number, code) tuples.
  • format_change(change): the change as text, the way Claude will see it.

  2. 2

    Write parse_diff

    In reviewer.py, the starter has:

    reviewer.py
    def parse_diff(text):    """Split a unified diff, the output of git diff, into one FileChange per changed file.    Deleted files are left out: there is no new code in them to review."""    # TODO milestone 1: return a list of FileChange, one per file in the diff.    # Watch for "+++ b/<path>" (a new file starts) and "@@ -a,b +c,d @@" (a hunk starts at line c).    raise NotImplementedError("milestone 1: parse_diff")

    Go through text.splitlines() once, keeping three counters: old lines left in the hunk, new lines left, and the next new line number.

    • A + line gets the current number, then the number goes up.
    • A context line (space) gets a number too, and both counts go down.
    • A - line has no number in the new file: store None.
    • A deleted file shows as +++ /dev/null. Leave it out: there is no new code to review.
    • Between two hunks of one file, add a ("@", None, "") row, so the gap shows.

    Counting lines left in the hunk, rather than looking for ---, matters: a removed line that starts with -- would look like a header.

Stuck?

Hint 1

Keep current, the FileChange being filled, and append rows to current.rows. Start a new one at each +++ line; read the counts from the hunk header with the HUNK regex already in the file: HUNK.match(line) gives the old count, the new start and the new count.

Hint 2

When a header has no count, as in @@ -1 +1 @@, the count is 1: int(hunk[1] or 1). Skip lines starting with a backslash: \ No newline at end of file isn't code.

The solution

Compare it with yours line by line, then type the difference rather than pasting: you learn more from the errors.

reviewer.py
def parse_diff(text):    """Split a unified diff, the output of git diff, into one FileChange per changed file.    Deleted files are left out: there is no new code in them to review."""    changes, current = [], None    old_left = new_left = number = 0  # lines left in the current hunk, and the next new line number    for line in text.splitlines():        if old_left > 0 or new_left > 0:  # inside a hunk, every line is code            mark, code = line[:1], line[1:]            if mark == "-":                current.rows.append(("-", None, code))                old_left -= 1            elif mark == "+":                current.rows.append(("+", number, code))                number, new_left = number + 1, new_left - 1            elif mark != "\\":  # a context line; "\ No newline at end of file" is skipped                current.rows.append((" ", number, code))                number, old_left, new_left = number + 1, old_left - 1, new_left - 1        elif line.startswith("+++ "):            path = line[4:].split("\t")[0]            current = FileChange(path.removeprefix("b/"))            if path != "/dev/null":                changes.append(current)        elif (hunk := HUNK.match(line)) and current:            if current.rows:                current.rows.append(("@", None, ""))  # a gap between two hunks            old_left = int(hunk[1] or 1)            number, new_left = int(hunk[2]), int(hunk[3] or 1)    return changes
reviewer.py
def format_change(change):    """One file's change as Claude sees it: + added, - removed, and line numbers from the new file."""    lines = [f'<file path="{change.path}">']    for mark, number, code in change.rows:        lines.append("       ..." if mark == "@" else f"{mark} {number or '':>4} | {code}")    lines.append("</file>")    return "\n".join(lines)

If it breaks

AttributeError: 'NoneType' object has no attribute 'rows'
A row arrived before any +++ line set current. Check that you only read rows while inside a hunk.
AssertionError: 16 != 17
Line numbers are one off. The hunk header's new start is the number of its first line, and only + and context lines move it on.
test_one_change_per_file_and_deleted_files_left_out
The deleted file shop/legacy_prices.py is in your list, or its path still starts with b/. Use path.removeprefix("b/").

Ask for a structured review

Define the shape of a finding, and ask Claude for a review in exactly that shape. Your first API call, for under a cent.

About 1 hourUses E3, E4, E5

A review in free text can't be checked, sorted or turned into a report. With output_format, the API makes Claude's answer match a Pydantic model, and the SDK hands it back as an object, as in E4. Typing severity as Literal["high", "medium", "low"] means it can only ever be one of those three words.

What you write

  • Finding: file, line, severity, issue and fix.
  • Review: findings (a list of Finding) and summary.
  • ask(messages, repo, cost): the call, and the tool-use loop from E5.

    Write the two models

reviewer.py

reviewer.py
def ask(messages, repo, cost):    """Call Claude until it answers with a Review, running the read_file calls it makes on the way."""    reads = 0    while True:        response = client.messages.parse(            model=MODEL, max_tokens=8000, system=SYSTEM, tools=TOOLS, messages=messages,            output_format=Review,  # the answer is checked against Review, and given back as parsed_output        )        cost.add(response.usage)        messages.append({"role": "assistant", "content": response.content})        if response.stop_reason != "tool_use":            return response        results = []  # one tool_result for every tool_use, all sent back in one message        for block in response.content:            if block.type == "tool_use":                reads += 1                print(f"  -> {block.name}({json.dumps(block.input)})", file=sys.stderr)                text, failed = run_tool(block.name, block.input, repo, reads)                results.append({"type": "tool_result", "tool_use_id": block.id, "content": text, "is_error": failed})        messages.append({"role": "user", "content": results})

3 · Milestone 3 of 5

Check every finding

The schema guarantees the shape of an answer, not that it's right. Check that every finding points at a line the change added, and ask again when one doesn't.

About 45 minutesUses E4

line: 22 is a valid integer, and it may point at a blank line, a removed line, or a file that isn't in the diff. A reviewer that cites the wrong line wastes the reader's time and loses their trust. So check in code, send the problems back, and ask again: the E4 pattern. If findings are still wrong after the last attempt, drop them rather than crash: a pre-commit check that fails for its own reasons gets switched off.

What you write

  • check(review, changes): a list of problems, one for each finding that doesn't point at an added line.
  • review(changes, repo, attempts=2): ask, check, retry with the problems listed, and drop findings still wrong at the end.
  1. 1

    Write check

    Build {change.path: change.added for change in changes} once. A finding is wrong if its file isn't a key, or its line isn't in that file's added lines. Write each problem as an instruction Claude can act on, such as "shop/db.py line 18 is not an added line. Use the number of a line marked +."

  2. 2

    Write review

    Start the conversation with build_prompt(changes) and a fresh Cost(). Then up to attempts times:

    • Call ask. If stop_reason isn't "end_turn", raise RuntimeError: the answer is cut off or was declined.
    • Check it. No problems: return the review and the cost.
    • Otherwise add a user message listing the problems, and go round again.

    After the last attempt, keep only the findings on added lines and return those. Print what happened to sys.stderr, so it doesn't mix with the report.

reviewer.py
def check(review, changes):    """Problems the schema can't catch. An empty list means every finding points at an added line."""    added = {change.path: change.added for change in changes}    problems = []    for finding in review.findings:        if finding.file not in added:            problems.append(f"{finding.file} is not in the diff. Use a path from a <file> tag.")        elif finding.line not in added[finding.file]:            problems.append(f"{finding.file} line {finding.line} is not an added line. Use the number of a line marked +.")    return problems
reviewer.py
def review(changes, repo=".", attempts=2):    """Ask for a review, check it, and ask again with the problems listed if it fails.    Returns the review and what it cost."""    messages = [{"role": "user", "content": build_prompt(changes)}]    cost = Cost()    for attempt in range(1, attempts + 1):        response = ask(messages, repo, cost)        if response.stop_reason != "end_turn":  # cut off or declined: no complete answer            raise RuntimeError(f"Claude stopped early ({response.stop_reason}).")        result = response.parsed_output        problems = check(result, changes)        if not problems:            return result, cost        print(f"Attempt {attempt}: {len(problems)} finding(s) point at the wrong place.", file=sys.stderr)        messages.append({"role": "user", "content": "Fix these problems and answer again:\n" + "\n".join(problems)})    added = {change.path: change.added for change in changes}  # still wrong: keep the findings that are right    result.findings = [f for f in result.findings if f.line in added.get(f.file, {})]    return result, cost

4 · Milestone 4 of 5

Let it read files

The diff hides context. Give Claude a tool to read files, and make it safe: inside the repo only, never secrets, and a limit on how much it reads.

About 1 hourUses E5, E10

Two planted bugs are hard to see from the diff alone. The refund bug depends on payments.py, which says PayGate refunds whatever it is sent; the reset-link default depends on RESET_LINK_HOURS in config.py. A tool lets Claude look. A tool that reads files is also the riskiest thing in this project: a path like ../../.ssh/id_rsa is a , and a prompt injection hidden in the code under review could ask for one. So the code decides what is allowed, not the model.

What you write

  • read_file(repo, path, start, end): numbered lines from a file inside the repo.
  • run_tool(name, args, repo, reads): runs read_file, enforces MAX_READS, and turns errors into error results.
  1. 1

    Write read_file

    Resolve both paths, then compare:

    The containment check
    root = Path(repo).resolve()target = (root / path).resolve()   # "../" and links are worked out hereif not target.is_relative_to(root):    raise ValueError(f"{path} is outside the repo.")
    • Refuse any file whose name starts with .env, even inside the repo.
    • Raise ValueError for files that don't exist.
    • Clamp the range: from line 1 at least, to the end of the file at most, and never more than MAX_LINES lines.
    • Number the lines as format_change does: f"{n:>4} | {line}".
  2. 2

    Write run_tool

    Unknown tool name: an error. Over MAX_READS: an error that tells Claude to finish. A ValueError from read_file: its message, as an error. Errors go back to Claude with is_error, so it can adjust; they never crash the review.

def read_file(repo, path, start, end):    """Lines start to end of a file in the repo, numbered. Refuses anything outside the repo,    and .env files, which hold secrets."""    root = Path(repo).resolve()    target = (root / path).resolve()    if not target.is_relative_to(root):        raise ValueError(f"{path} is outside the repo.")    if target.name.startswith(".env"):        raise ValueError("read_file can't open .env files.")    if not target.is_file():        raise ValueError(f"There is no file {path} in the repo.")    lines = target.read_text(encoding="utf-8", errors="replace").splitlines()    start = max(start, 1)    end = min(end, start + MAX_LINES - 1, len(lines))    if start > end:        return f"{path} has {len(lines)} lines."    return "\n".join(f"{n:>4} | {lines[n - 1]}" for n in range(start, end + 1))

def git_diff(repo=".", staged=False):    """The uncommitted changes in a git repo, or only the staged ones."""    command = ["git", "diff", "--staged"] if staged else ["git", "diff", "HEAD"]    result = subprocess.run(command, cwd=repo, capture_output=True, text=True, encoding="utf-8")    if result.returncode != 0:        raise RuntimeError(result.stderr.strip() or "git diff failed.")    return result.stdout

def to_markdown(review, cost):    """The review as a Markdown report: worst findings first."""    lines = ["# Code review", "", review.summary, ""]    if review.findings:        lines += ["| Severity | Where | Issue | Fix |", "|---|---|---|---|"]        for f in sorted(review.findings, key=lambda f: (-SEVERITY[f.severity], f.file, f.line)):            cells = [f.severity, f"`{f.file}:{f.line}`", f.issue, f.fix]            lines.append("| " + " | ".join(cell.replace("|", "\\|").replace("\n", " ") for cell in cells) + " |")    else:        lines.append("No findings.")    lines += ["", f"{len(review.findings)} finding(s) · {cost.calls} model call(s) · ${cost.dollars():.4f}"]    return "\n".join(lines) + "\n"

def should_block(review, fail_on="high"):    """True if any finding is at the fail_on severity or worse. fail_on="never" never blocks."""    if fail_on == "never":        return False    return any(SEVERITY[f.severity] >= SEVERITY[fail_on] for f in review.findings)

def main(argv=None):    parser = argparse.ArgumentParser(description="Review a code change with Claude.")    parser.add_argument("diff", nargs="?", help="a saved diff; leave it out to review your uncommitted changes")    parser.add_argument("--repo", default=".", help="the repo the diff comes from, for read_file (default: here)")    parser.add_argument("--staged", action="store_true", help="review only staged changes, before a commit")    parser.add_argument("--fail-on", choices=["high", "medium", "low", "never"], default="high",                        help="exit with code 1 if a finding is this bad or worse (default: high)")    parser.add_argument("--prompt", action="store_true", help="print what Claude would see, and stop")    args = parser.parse_args(argv)    text = Path(args.diff).read_text(encoding="utf-8") if args.diff else git_diff(args.repo, args.staged)    changes = parse_diff(text)    if not changes:        print("No changes to review.")        return 0    if args.prompt:        print(build_prompt(changes))        return 0    result, cost = review(changes, args.repo)    report = to_markdown(result, cost)    Path("review.md").write_text(report, encoding="utf-8")    print(report)    if should_block(result, args.fail_on):        print(f"Blocked: a finding is {args.fail_on} severity or worse.
