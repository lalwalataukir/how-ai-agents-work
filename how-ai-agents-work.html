Stage 1 · Ideation

Decide whether you need an agent at all

Before anyone writes code, be clear about what an agent is, whether your problem needs one, and what "good" looks like.

Chatbot, workflow or agent?

All three can use the same . The difference is who decides the next step.

ChatbotAgent
Who decides the next stepThe user, one message at a timeA developer, in advance, in codeThe model, while it works
Research exampleAnswers from what it already learned in training. No live sources.Always: search the question, take the top 3 results, summarise them.Chooses what to search, which results are worth reading, and when it has enough.
Good forQuick Q&A, drafting, brainstormingRepeatable processes with known stepsOpen-ended tasks where the steps depend on what it finds
Main riskOut-of-date or made-up factsBreaks when a case doesn't fit the scriptUnpredictable path, higher cost, harder to test
Plain definition. An agent is an LLM that works in a loop. It decides on an action, uses a to carry it out, looks at the result, and decides again, until the goal is met.

It's a spectrum, not three boxes

Real systems sit somewhere between "the developer decides everything" and "the model decides everything". Each step to the right gives the model more freedom, and costs more to test and to trust.

Who decides whatResearch assistant at this level
1 · Fixed workflowThe developer decides every step. No LLM, or an LLM only writes text.Search the question, take the top 3 results, paste them into a template.
2 · Workflow with LLM stepsThe developer decides the steps. The LLM does the work inside some of them.Same fixed steps, but an LLM writes the summary.
3 · RouterThe developer draws the possible paths. The LLM picks which path to take.An LLM grades the results: good ones go to reading, poor ones to a rewritten search.
4 · Agent on a mapThe developer draws the map and its limits. The LLM decides what to do at each stop, and how many times to go round a loop.The graph you'll meet in modules 2 to 4: plan, search, grade, rewrite, read, write, with human review.
5 · Open agent loopThe LLM decides every step, from a list of tools, until it's done or a limit stops it.The demo above: the model chooses each search, page and note.
Why this matters. Most production "agents" sit at levels 3 and 4. Modules 2 to 4 build the research assistant as a graph a developer drew, where the model chooses the route and the content but not the map. That's still agentic, just with fences. Choose the lowest level that handles your real cases.

When is an agent the right choice?

Answer these four questions. If you can't say "yes" to at least the first two, a workflow is usually cheaper, faster and easier to trust.

  • 1Do the steps depend on what it finds along the way? The research assistant can't know which sources it will need until it sees the search results.
  • 2Does it need tools to act or fetch information? Yes: it has to search and read live web pages.
  • 3Can mistakes be caught or undone? A draft report can be checked before anyone relies on it. Sending money cannot be undone.
  • 4Is the task worth the extra cost and wait? An agent may call the model 5 to 20 times per task, not once.

Define the job, the users and what success means

Write this on one page before design starts. The success criteria become your tests in Stage 4.

Job

Given a question, find credible sources, read them, and write a report of about 150 words with a citation for every claim.

Users

Analysts and PMs who need a quick, sourced briefing before a meeting. They will skim it and click through to the sources.

Success criteria
  • At least 3 sources, all actually read
  • 0 made-up citations
  • Done in under 60 seconds
  • Costs under ₹5 per report
  • 4 out of 5 average user rating
Out of scope

Personal advice (medical, legal, investment), questions about private company data, and anything that sends messages or spends money.

Today's baseline

An analyst spends about 40 minutes on a sourced briefing. A plain workflow (search, take the top 3, summarise) takes 10 seconds and costs under ₹1, but often cites junk.

What we must beat

The agent has to be clearly better than the plain workflow on source quality, and much faster than the analyst. If it isn't, ship the workflow.

Stage 2 · Design

    
The five parts of every agent

    
Every agent, however complex, is built from the same parts. Here is what each one is for our research assistant.

  


  

    

      

        1 · The model
        
The decision-maker

        
An LLM that reads everything in memory and decides the next step: think, use a tool, or give the final answer. You reach it through an  and pay per .

      

      

        2 · The instructions
        
The job description

        
A  that sets the role, the rules and when to stop. It's sent to the model at the start of every turn.

        
You are a research assistant. Answer the user's question in a report of about 150 words. Use at least 3 credible sources. Cite every claim as [n]. Only cite pages you have opened with fetch_page. If sources disagree, say so. If you can't find good sources, say that instead of guessing.

      

      

        3 · Tools
        
The hands

        
Functions your code can run when the model asks. Ours has four:

        
    
          
  • web_search: find pages for a query
    • 
          
  • fetch_page: open one page and return its text
    • 
          
  • save_note: write key facts to a scratchpad
    • 
          
  • write_report: save the final report to a shared folder
    • 
        

      

      

        4 · Memory
        
What it knows right now

        
Short-term memory is the running conversation: instructions, question, and every step and result so far. It lives in the model's .

        
Long-term memory is stored outside the model and fetched when needed, for example "this user prefers bullet points". Our first version doesn't need it.

        
The limit: every step adds text, and the context window has a ceiling. Long runs get slower, cost more and can fill it up. Keep tool results short, save key facts as notes, and summarise or drop old steps.

      

    

  


  

    
Choosing the model

    
There's no single best model. Bigger models plan and write better, and smaller ones are cheaper and faster. Many teams use both: a large model for the steps that need judgement, and a small one for simple checks.

    

      

        
QuestionWhy it mattersFor our research assistant

        
          
How good is it on our test cases?Public benchmarks don't measure your task. Your eval set (Stage 4) does.Compare 2 or 3 models on the same 30 questions before choosing.

          
What does one run cost?An agent calls the model 5 to 20 times per task, so price differences multiply.Large model to plan and write, small model to grade search results.

          
How long do users wait?Each call adds seconds. Smaller models answer faster.Target: under 60 seconds per report.

          
Is the context window big enough?Three full web pages plus instructions can be tens of thousands of tokens.Trim pages to their main text before adding them to memory.

          
Where does our data go?Providers differ on data retention, training use and region.Fine for public web pages. Check carefully before adding client data.

          
Can we pin the version?Providers update models. An unpinned name can change behaviour overnight.Use a dated model version, and re-run evals before moving to a new one.

        
      

    

  


  

    
5 · The loop: plan, act, observe, repeat

    
The fifth part ties the others together. The agent runs this cycle until it decides it has enough to finish, or until a limit stops it. When the demo is running, the current phase lights up below.

    
  


  

    
One agent or several?

    
Some systems use an  agent that splits a task and hands the parts to worker agents. That adds handoffs, and every handoff can lose information.

    
    

      
Start here
One agent
  • Easier to build, test and debug
  • One memory, so nothing is lost in handoffs
  • Right for our research assistant v1

      
Only when needed
Several agents
  • The task splits into independent parts that can run in parallel (for example, "compare India and the US")
  • Parts need different tools or permissions
  • One memory would get too long
  • Usually costs several times more tokens

Stage 3 · Build

    
How the parts connect

    
The surprising part for most PMs: the model never does anything by itself. It only writes text. Your code does everything else.

  


  

    
Who talks to whom

    
    

      
The model writes requests
A  is just structured text, such as fetch_page(url="…"). Nothing happens until your code acts on it.

      
Your code holds the power
It checks the request, runs the tool, catches errors, and stops the loop when a limit is hit.

      
Memory is re-sent every turn
The model has no memory between calls, so all of it is sent again each turn. That's why cost goes up with every step.

    

  


  

    
The agent loop in about 10 lines

    
This is : a simplified sketch of real code. When the demo is running, the line for the current step is highlighted.

    
function run_agent(question):  memory = [instructions, tool_list, question]  for step in 1 .. MAX_STEPS:    reply = model.next_step(memory)    if reply.is_final_answer:      return check_citations(reply)    if reply.tool needs_approval:      wait_for_human_ok()    result = run_tool(reply.tool, reply.args)    memory.add(reply, result)  return "Stopped: step limit reached"

    

      
Reading it in plain English

        
    
          
  • memory = … Start with the instructions, the list of tools and the user's question.
    • 
          
  • for step in 1 .. MAX_STEPS Repeat, but never more than a set number of times. This is your first .
    • 
          
  • model.next_step Send all of memory to the model and ask what to do next.
    • 
          
  • if final answer Check the answer (for example, its citations) and return it.
    • 
          
  • needs approval For risky tools, pause until a person says yes.
    • 
          
  • run_tool / memory.add Run the tool and save the result, so the next turn can see it.
    • 
        

      

      
A tool definition

        
Each tool is described to the model in a short block like this, usually written as . The model chooses tools by reading the description, so the description is effectively part of the prompt.


{
  "name": "fetch_page",
  "description": "Open one web page and return its main text. Use after web_search to read a result in full. Do not use it to search.",
  "inputs": { "url": "the full address from a search result" }
}

      

    

    
You've seen this pattern before. When an agent fetches documents and answers from them, that's a form of . Our research assistant is RAG where the "retrieval" step is a web search the agent chooses itself.

  


  

    
When a tool fails

    
Tools fail all the time: a search times out, a page is behind a login, a service is rate-limited. Your code decides what happens next, so decide it on purpose.

    

      
1 · Set a time limit
Every tool call gets a deadline, for example 10 seconds for fetch_page. A hung call shouldn't hold up the whole run.

      
2 · Retry briefly
For short outages, try again once or twice, waiting a little longer each time. Count retries towards the run's limits.

      
3 · Tell the model
If it still fails, send the error back as the tool's result, such as "page timed out, try another result". The model can then pick a different source instead of the run crashing.

      
4 · Fail honestly
If the agent can't get what it needs, it says so ("I could only verify 2 sources") rather than filling the gap from memory.

    

  


  

    
Plugging in tools with MCP

    
Writing a connector for every service gets old fast. The  is an open standard for this. A service publishes its tools once as an MCP server, and any agent that speaks MCP can use them: search engines, Google Drive, Slack, GitHub, your own database.

    
    

      
What it gives you
  • Ready-made tools for many popular services
  • One way to connect them, instead of one connector per service
  • The same tools work across agent frameworks and apps

      
What to watch
  • An MCP server is code you're trusting. Use ones from the service's owner or that you've reviewed.
  • Expose only the tools the agent needs. A CRM server with "delete client" doesn't belong in a research assistant.
  • Tool descriptions come from the server and go straight to the model, so a bad server can inject instructions.

Stage 4 · Test

    
Prove it works, then try to break it

    
Agents take a different path each time, so "I tried it and it looked fine" isn't enough. You need repeatable checks across many examples.

  


  

    
Test cases and evals

    
A  is one example input plus what should happen. An  runs many test cases automatically and scores the results, so you can compare versions after every change. Some checks are simple code rules. For fuzzier qualities you can use an .

Start with 20 to 50 test cases drawn from real user questions. Add a new one every time you find a bug.

  


  

    
Setting the bar when the answer changes every run

    
Run the same question twice and an agent may take a different path. One pass proves little. Good evals account for that.

    

      
Run each case several times
Run every test case 3 to 5 times and record its pass rate, not pass or fail. A case that passes 3 times out of 5 is a real problem, even if it passed the one time you tried it.

      
Split hard rules from quality
Hard rules must pass every time: no made-up citations, a disclaimer where needed, no out-of-scope answers. Quality scores, like clarity, get a target average.

      
Set the bar from a baseline
Score the plain workflow (or today's manual process) on the same cases first. The bar is "beats the baseline on quality, with zero hard-rule failures", not a number picked in a meeting.

      
Check the path, not just the answer
The trace shows how it got there. Did it read before citing? Did it take 6 steps or 20? A right answer reached by a lucky, wasteful path will fail next week.

Before launch: offline evals
Your saved test cases, run on every prompt, model or tool change. They tell you whether a change is safe to ship.

      
After launch: online evals
Automatic checks and a judge running on a sample of real traffic, plus user ratings. They tell you whether it's still working on questions you didn't think of.

    

  


  

    
How agents fail

    
These are the failure modes you'll see most often. Press "Show me" to replay one in the demo.

    

      

        Wrong tool call
        
It asks for a tool that doesn't exist, picks the wrong tool, or passes bad inputs.

        
Fix: few tools with clear, distinct names and descriptions. Return a helpful error so it can correct itself.

        
      

      

        Looping
        
It repeats the same action because it never feels "done", using up time and money until something stops it.

        
Fix: a step limit, detection of repeated identical calls, and instructions that define "good enough".

        
      

      

        Hallucination
        
A  is when the model states something made up as fact. Here, it invents a statistic and a source.

        
Fix: a code check that every citation matches a page it actually read. Ask the model to say "I don't know". A real citation can still be wrong, so also check that the page supports the claim.

        
      

      

        Prompt injection
        
A web page contains hidden text such as "ignore your instructions and…". The agent reads it and may obey it.

        
Fix: treat everything tools return as data, not orders. Limit what tools can do, check the output, and require approval for risky actions.

Stage 5 · Ship

    
Launch with limits, then keep watching

    
Shipping an agent means deciding what it may do on its own, what needs a person, what it may cost, and how you'll know when it goes wrong.

  


  

    
Guardrails at every point in the run

    

      
Before
Check the input
  • Reject out-of-scope requests (for example, personal investment advice)
  • Flag likely prompt injection

      
During
Limit the run
  • Only these 4 tools are allowed
  • At most 24 steps (about 12 model calls) and ₹10 per run
  • Time limit on each tool call

      
After
Check the output
  • Every citation was actually read
  • Required disclaimers are present
  • No personal data in the report

    

  


  

    
Human approval steps

    
A  step pauses the agent until a person approves. Use it where a mistake would be costly, public or impossible to undo, and nowhere else. Too many approvals and people start clicking "yes" without reading.

    

      

        
ActionRiskApproval?

        
          
web_search, fetch_pageRead-only, nothing changesNo

          
save_notePrivate scratchpad, easy to undoNo

          
write_report to shared folderColleagues will see and rely on itYes, for v1

          
Email the report to 2,000 clientsPublic, can't be undoneAlways

Monitoring after launch

    
Agents drift. Websites change, users ask new things, and model updates change behaviour. Good  lets you see what happened in any run.

    

      
Log every run
Save the full trace: each model call, tool call, result, tokens, cost and time. It's what the demo's Log panel shows.

      
Track on a dashboard
  • Task success rate
  • Cost per task
  •  wait time
  • Steps per run
  • Approval rejections and user ratings

      
Alert and learn
Alert on spikes in cost, errors or step limits hit. Each week, review a sample of bad runs and turn each one into a new test case.

      
Let users flag bad answers
Put a thumbs up and down on every report, with an optional reason ("wrong source", "too long", "missed the point"). Save it on the run's trace so you can open the exact run behind each complaint.

    

  


  

    
Roll out in stages, with an off switch

    
Don't go from zero to every user in one day. Each stage has a clear bar for moving on, and you can step back at any point.

    

      

        
StageWhoMove on when

        
          
ShadowRuns on real questions, but nobody sees the outputHard rules pass on real traffic, and cost and wait are within budget

          
InternalYour own team, for a week or twoNo open serious bugs, and the team would use it themselves

          
BetaAbout 5% of users, who know it's newRatings and complaint rate at or better than target

          
GeneralEveryone, in steps: 25%, 50%, 100%Metrics hold at each step

        
      

    

    

      
Kill switch
One setting that turns the agent off and shows a fallback, such as the plain workflow or "try again later", without a code release.

      
Pin the model
Use a dated model version. Treat an upgrade like any other change: run the evals first, then roll it out in stages.

      
Know who's on call
Decide who gets the alert, and what they're allowed to do: pause, roll back or switch off.

Glossary

      

    

  







  

    
Learn from others

    
3 common mistakes teams make

  

  

    

      1
      
Building an agent when a workflow would do

      

        
What it looks like
A fixed, repeatable process becomes slow, expensive and unpredictable, because the model is "deciding" steps that never change.

        
Fix
Start with the simplest thing that works. Use an agent only for the part of the task that is truly open-ended.

      

    

    

      2
      
Shipping without evals or limits

      

        
What it looks like
A prompt tweak fixes one case and quietly breaks three. A looping run burns through budget overnight and nobody notices until the bill arrives.

        
Fix
Have 20 to 50 test cases before launch and run them on every change. Set step and cost limits from day one.

      

    

    

      3
      
Vague tools and instructions

      

        
What it looks like
Tools with overlapping names ("search", "find", "lookup") and one-line descriptions lead to wrong tool calls, made-up inputs and loops.

        
Fix
Keep a few tools with distinct names. Say when to use each one and when not to. Give helpful error messages, and define "done" in the instructions.
