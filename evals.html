1 · Error analysis first

Read failures before you measure anything

Generic scores such as "helpfulness" or "coherence" rarely match what actually goes wrong. tells you what to measure.

  1. Read 50 to 100 traces from real or realistic use. Module 5 shows how to find them in Langfuse.
  2. Write one note per failure in plain words: "cited a page it never opened", "ignored 'focus on India'".
  3. Group the notes into a handful of categories and count each one.
  4. Fix the cheap ones now. Many need only a clearer instruction or tool description.
  5. Write an eval for each category that matters, starting with the most frequent and the most harmful.

2 · The dataset

Build a small dataset you trust, then grow it

An is a list of inputs, each with what a good answer must do. Twenty good cases beat a thousand you've never read.

Typical, about 60%

Real questions from traces, in the mix users actually ask. Remove personal data first.

Edge cases, about 30%

No good sources, sources that disagree, vague questions, follow-ups, other languages.

Adversarial, about 10%

Pages with hidden instructions, requests it should refuse. Module 9 lists attacks to include.

How big

Start with 20 to 50 cases to catch big problems. Grow to 100 to 300 as the product matures, so small differences become visible (section 7).

Keep it alive

Add every production failure as a new case. Retire cases that no longer reflect how people use the product. Keep a version number so scores stay comparable.

4 · Judge calibration

Check the judge before you trust its numbers

An uncalibrated judge can report 90% when careful reviewers would pass 40%, as the demo shows. Calibrating means measuring its with people, then fixing the rubric.

  1. People label 50 to 100 outputs pass or fail, with a one-line reason. Ideally the PM or a domain expert.
  2. Run the judge on the same outputs and compare.
  3. Count both kinds of mistake. hide problems; false fails waste time.
  4. Read every disagreement and change the : add the missing criterion, add an example.
  5. Repeat until agreement is high, around 90% or more, then re-check every month and after model changes.
Rubrics that work
  • Pass or fail per criterion, not a 1 to 10 score
  • One judge per criterion when they are unrelated
  • Reasoning first, verdict last
  • One pass and one fail example
  • The question and sources included, not only the answer
Known judge biases
  • Prefers longer answers
  • Prefers confident wording
  • Prefers the first option in a side-by-side
  • Prefers text written by its own model family

5 · Repeats

pass@k and pass^k: agents don't do the same thing twice

The same question can succeed on one run and fail on the next. Run each case several times and choose the number that matches how the product is used.

At least one of k runs succeeds. Fits a person who can retry or choose between drafts.

70% per run → pass@3 = 97%

All k runs succeed. Fits an agent that acts on its own, where every run must work.

70% per run → pass^3 = 34%

Same agent, same 70%. Which number you report changes the story, so say which one you mean. Three to five runs per case is usually enough to see how consistent it is.

6 · Offline and online

A gate before release, and a watch after

Offline: the CI gate
  • The dataset runs on every prompt, tool or model change
  • A blocks the change if the pass rate drops more than an agreed margin
  • Critical cases, such as safety and refusals, must all pass
  • Catches before users see them
Online: live traffic
  • judge a sample of real traces every day
  • Thumbs up or down, edits and retries as user signals
  • Alerts when a score drops
  • Finds failures the dataset doesn't have yet; add them as new cases

Modules 6 and 7 cover which production numbers to watch and how to roll out safely.

7 · Comparing versions

Is version B really better than version A?

Small datasets are noisy. With 50 cases and a pass rate around 80%, the score moves by about ±6 points from chance alone. With 200 cases it's about ±3.

Same cases, same runs

Run both versions on the same dataset version, with the same number of repeats and the same judge.

Compare case by case

A counts the cases B fixed and the cases B broke. "Fixed 9, broke 2" says more than "84% vs 82%".

Read the flips

Open every case that changed result. A version that fixes length but breaks citations may not be better at all.

8 · Weekly ritual

Make it a habit, not a project

Evals decay if nobody looks at them. An hour a week keeps them honest.

  1. Monday · 30 min
    Read 20 to 30 traces

    Low-scoring and thumbs-down ones first. Note new failure types.

  2. Monday · 10 min
    Add new cases

    Every new failure becomes a dataset case, labelled by a person.

  3. Wednesday · 10 min
    Spot-check the judge

    Label 10 judged outputs yourself. If agreement slips, fix the rubric.

  4. Friday · 10 min
    Review the numbers

    Pass rate by category, online scores, and what changed this week. Decide the top failure to fix next.

Keep this

One-page cheat sheet

Read failures → write evals for them → check the graders → gate releases → repeat every week.

Checklist

  • Categories come from reading real failures
  • Dataset: typical, edge and adversarial cases, versioned
  • Code checks wherever a rule will do
  • LLM judge calibrated against people, ~90% agreement
  • 3 to 5 runs per case; pass@k or pass^k stated
  • CI gate on every change; online evals on live traffic

Questions to ask

  • Which failure categories do our evals cover?
  • How often does the judge agree with people?
  • How many cases, and how many runs each?
  • Which cases did this change fix, and which did it break?
  • When were production failures last added?

Numbers to watch

  • Pass rate by failure category
  • Judge agreement and false-pass rate
  • pass^k on critical tasks
  • Cases fixed vs broken per release

3 common eval mistakes

1

Off-the-shelf scores instead of your failures

What it looks like
The dashboard tracks "helpfulness 8.2/10" while users complain about missing citations, which nothing measures.
Fix
Start from error analysis and write an eval for each failure category that matters.
2

Trusting a judge nobody checked

What it looks like
The judge reports 90% pass. Customers find problems in a third of answers.
Fix
Label a sample yourself, measure agreement and false passes, and fix the rubric until it matches.
3

A dataset that never changes

What it looks like
Scores climb every release, but only on the 40 cases the team has tuned against for months.
Fix
Add production failures every week, and keep some cases the team doesn't tune against.
