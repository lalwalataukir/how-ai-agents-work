Context engineering: decide what the model sees

A model only knows what's in its on each call. Put in the right things, in the right order and at the right size, and an ordinary model does great work. Stuff it full, and the best model gets slow, expensive and confused. This module shows how to manage that budget for the research assistant.

1 · The window

What's in the context window

Every call sends the whole window. These are the parts, in the order that usually works best, with typical sizes for one call of the research assistant.

Instructions (system prompt)300 to 1,000 tokens
Tool definitions150 to 300 per tool
Examples (few-shot)200 to 600 each
User memory (preferences)50 to 300
Retrieved text (pages, documents)1,000 to 20,000+
Conversation historygrows every turn
Tool results from this rungrows every step

Everything costs

You pay for every on every call. An agent makes 5 to 20 calls per task, so a bloated window is paid for many times over.

More isn't better

Models are distracted by irrelevant text, and use facts in the middle of a long context less well. A focused window often scores higher than a full one.

It's a product decision

What the agent knows, remembers and is told decides how it behaves. Most of these choices need no new code, just decisions.

2 · Instructions

Writing instructions that work

The is the agent's job description. Treat it like product copy: drafted carefully, reviewed, versioned and tested.

Include
  • Role and goal: who it is and what "done" looks like
  • Rules that matter: cite every claim, at least 3 sources
  • Output format: length, structure, citation style
  • When unsure: say so, don't guess
  • When to stop: what counts as enough
  • One good example, if format matters
Leave out
  • Long lists of "never do X" for unlikely cases
  • Rules that contradict each other
  • Background the model doesn't need for this task
  • Instructions that belong in a tool description
  • Shouting: "VERY IMPORTANT!!!" doesn't help
Vague
You are a helpful assistant. Answer research questions well. Be accurate.

The model has to guess the length, sources, format and what to do when evidence is thin.

Clear
You are a research assistant for analysts. Answer in about 150 words: a one-line answer first, then the detail. Use at least 3 sources you have opened with fetch_page, and cite each claim as [n]. If sources disagree, say so. If you can't find good sources, say that instead of guessing. Stop once the answer is supported.

Every sentence changes behaviour, and each one can be tested.

3 · Tools as context

Tool definitions are part of the prompt

Each tool's name, description and inputs are sent on every call. They cost tokens, and every extra tool is one more option the model can pick wrongly.

Fewer, clearer tools

Four well-described tools beat forty overlapping ones. Wrong-tool errors rise as the list grows.

Load tools per task

Connecting several MCP servers can add dozens of tools. Load only the ones this task needs, or let the agent search for a tool when it needs one.

Keep results small

A tool that returns a whole web page fills the window. Return the main text, or the relevant passages, plus a way to ask for more.

5 · Long runs

Keeping long runs small

Every step adds tool results to the window. A 20-step run can fill it, and cost climbs with every call. Four techniques keep it in check.

Trim tool results

Keep the part of each result the agent will use. Drop the rest, or replace old results with a one-line note of what they contained.

Summarise as you go

replaces older turns with a short summary once the window passes a threshold. Check the summary keeps decisions, open questions and sources.

Notes outside the window

The agent writes key findings to a scratchpad or file, and reads back only what it needs. The research assistant's save_note tool does this.

Hand off to a sub-agent

A reads 10 pages in its own fresh context and returns a 200-word summary. The main agent's window stays small.

6 · Prompt caching

Pay less for the part that never changes

With , the provider reuses the unchanged start of your prompt from a recent call. Cached input is billed at a fraction of the normal price and is processed faster. Check each provider's current terms.

Order for caching
  1. Instructions
  2. Tool definitions
  3. Examples
  4. User memory
  5. Retrieved text and history
  6. The newest message

Stable parts first, changing parts last. The cache covers the longest unchanged prefix.

What breaks it
  • A timestamp or user name at the top of the instructions
  • Tools listed in a different order each call
  • Editing an early part of the history
  • Long gaps between calls, beyond the cache's lifetime

7 · When context goes wrong

Five context failures, and their fixes

A fact that was retrieved is missing from the answerRetrieve less; put the most relevant passages first; trim pages

DistractionAnswers drift towards earlier, unrelated topicsSummarise or drop old turns; start a fresh context for a new task
Clashing instructionsBehaviour flips between runsOne source of truth for each rule; remove contradictions

Keep this

One-page cheat sheet

Give the model what it needs, in a stable order, at the smallest size that still works, and measure every change.

Checklist

  • Instructions: role, rules, format, when unsure, when to stop
  • Only the tools this task needs
  • Tool results trimmed before they enter the window
  • History summarised past a threshold
  • Stable parts first, so caching works
  • Every context change run through the eval set

Questions to ask

  • How many tokens does a typical call send, and what's in them?
  • How many tools are loaded per call?
  • What happens when the window gets long?
  • What share of input is cached?
  • Can users see and correct what's remembered?

Numbers to watch

  • Tokens per call, and per run
  • Cache hit rate
  • Wrong-tool rate
  • Pass rate after each context change

Learn from others

3 common context mistakes

1

"The window is huge, so send everything"

What it looks like
Whole documents, every tool and the full history go in every call. Costs climb, answers get vaguer, and nobody knows why.
Fix
Start small and add only what improves the eval score.
2

Fixing quality with more instructions

What it looks like
Every bug adds a line to the system prompt. It grows to 3,000 words of rules that contradict each other.
Fix
Prune regularly. Move tool rules into tool descriptions, and test that each rule still earns its place.
3

Breaking the cache by accident

What it looks like
The current time is added to the top of the prompt "for context". Every call misses the cache, and the bill doubles.
Fix
Keep the start of the prompt identical across calls. Put anything that changes at the end.
